# Правило проекта: чистая сборка и совместное использование ресурсов

**Статус:** обязательное техническое правило. Проверка упаковки работает при сборке Vite, проверка совместной публикации выполняется до доставки Pages.
**Область действия:** обычная сборка Vite, экспериментальная сборка, совместная публикация GitHub Pages, автономный HTML, SVG и PixiJS/WebGL.  
**Цель:** минимальный размер поставки без потери качества графики, игровых ресурсов и функциональности.

## 1. Что разрешено включать в поставку

1. В `dist/` попадают только файлы, действительно необходимые для запуска и работы соответствующей версии игры. Папка `public/` — **не** разрешение на безусловное копирование её содержимого.
2. Запрещены любые каталоги с именем `_src` на любой глубине, PSD, рабочие исходники художника, промежуточные экспорты, референсы, временные результаты, неиспользуемые изображения и звуки. Для тестового канала отдельно разрешена собранная страница редактора локаций. Это правило относится к **публикуемым результатам**, а не к Git-репозиторию: исходники должны сохраняться в репозитории вне пакета игры.
3. Нельзя удалять нужные текстуры только потому, что путь не найден в статическом импорте. При определении используемых файлов необходимо учитывать `src/assets/manifest.js`, `src/boss/assets.js`, сгенерированные списки, шаблонные имена атласов, динамические выборы, HTML/CSS, предзагрузку, пользовательские настройки и режимы игры.
4. Результирующий список ресурсов должен быть явным и проверяемым (манифест/allowlist или эквивалентная проверка зависимостей). Неизвестные файлы из `public/` не должны автоматически попадать в публикацию. Любое исключение (например, иконки установки, manifest.webmanifest или необходимые файлы совместимости) документируется.
5. Сайт и автономный HTML имеют разные форматы распространения: автономный HTML вправе встраивать **уникальные необходимые** ресурсы, но не рабочие исходники; GitHub Pages хранит основной сайт в `/` и экспериментальную версию в `/test/`. Размер объединённого пакета публикации не равен размеру загрузки одной страницы.
6. Исходное качество, прозрачность, пиксельная графика, атласные координаты и детализация должны сохраняться. Потеря качества изображения ради размера без отдельного согласования недопустима.

## 2. Правило «один уникальный ресурс — одна загруженная текстура»

1. Для одного URL/идентификатора/варианта текстуры должен использоваться единый загрузчик и кэш (shared texture). Роботы, их части, декорации, портреты и эффекты могут иметь отдельные отображаемые экземпляры, но должны ссылаться на общий источник изображения.
2. В PixiJS несколько `Sprite` могут использовать одну `Texture`/`TextureSource`. Запрещено повторно декодировать или загружать одинаковый атлас для каждого робота, части или кадра; податласы/прямоугольники разрешены как ссылки на общий исходный ресурс.
3. В SVG общие `<defs>`/`<image>`/`<pattern>` и ссылки (`<use>` либо иная эквивалентная схема) предпочтительнее многократного создания длинных `data:image/...;base64` значений. Нельзя повторять идентичные Base64-строки в DOM для каждого сегмента, если возможно безопасное переиспользование без изменения рендеринга.
4. Отдельные состояния, координаты, цвета, повреждения, маски, кадры анимации и модификации не должны «протекать» между экземплярами из-за общего источника. Разные реально используемые варианты текстуры остаются самостоятельными ресурсами и кэшируются каждый по своему ключу.
5. Удаление экземпляра робота/спрайта/сцены освобождает его собственные объекты и подписки, но не уничтожает общую текстуру, пока её используют другие. Для общих ресурсов нужен контролируемый жизненный цикл с очисткой при завершении работы/сбросе кэша.
6. Повторяющиеся PNG в сохранённой браузером странице **не доказывают**, что WebGL создал столько же физических GPU-копий. Проверять отдельно: число запросов, декодированных изображений, GPU-текстур, DOM-узлов и размер сериализованного HTML. Сохраняемый браузером HTML не считать эквивалентом `npm run standalone`.

## 3. Проверка и критерии приёмки

Перед публикацией обеих веток и автономной версии требуется:

- `npm test` и соответствующие проверки сборки; `npm run build`, `npm run build -- --mode test`, `npm run standalone` — по назначению.
- Проверка `dist/`: ноль `_src` в любом участке пути, ноль `.psd`, отсутствие других исходников и неразрешённых файлов; наличие всех нужных ресурсов из используемых манифестов и путей.
- Отчёт с размерами `dist`, HTML, JS/CSS и активов по типам; отдельно размер основного и тестового сайта, их общего пакета и автономного HTML. Сравнивать однотипные показатели до/после (распакованные байты и сетевые переданные байты различаются).
- В сцене с несколькими одинаковыми пациентами один URL/атлас не должен загружаться/декодироваться для каждого пациента заново; проверить повторные бои, замену модификаций, смену арен, перезагрузку и освобождение ресурсов.
- Проверка SVG-рендерера на повторяющиеся крупные `data:image` значения: одинаковые данные должны по возможности ссылаться на одно объявление, а не размножаться по сотням элементов.
- Визуальные регрессии: обычный бой, Башня, боссы, хирургия, модификации, смена атласов, повреждения/отрыв конечностей, свет, мобильная и полная графика. Никаких изменений внешнего вида и механики.
- Если автоматическое определение динамического ресурса ненадёжно, сборка **не должна** молча удалять его: исправить манифест/исключение, после чего повторить проверку.

## 4. Порядок внедрения

1. Зафиксировать исходные размеры сборок и список реально используемых активов.
2. Исключить из поставки `_src`, PSD и другие рабочие файлы, не удаляя исходники из Git. Настроить автоматический контроль содержимого `dist`.
3. Разобраться с источниками повторных загрузок/декодирования и с общим кэшем в PixiJS и SVG. Не предпринимать замену GPU-объектов без измерения их фактического числа.
4. Оптимизировать сериализацию SVG/Base64 при сохранении ссылочной модели и неизменной графики.
5. Провести тесты, визуальную сверку и сравнить размеры и память до/после.

**Не допускается:** «уменьшить размер» путём потери нужных атласов, редактирования изображений без согласования, отключения игрового контента или подмены формата автономной версии.

## 5. Состояние на момент принятия правила (20.11.2026)

При аудите ветки `experiment/tower-bosses` папка `public/` составляла около 22,30 МиБ, из них `public/assets/textures/UI/_src/` — около 12,35 МиБ, PSD внутри `public` — около 11,42 МиБ (категории пересекаются). В `vite.config.js` включено `sourcemap: true`. Публикация Pages собирает **два отдельных** сайта: `main` и `experiment/tower-bosses`. Это исходные наблюдения, а не подтверждение внедрённой оптимизации. Размер сохранённой браузером HTML-страницы не следует приравнивать к весу распространяемой игры.

## 6. Первая реализация упаковки (20.11.2026)

В экспериментальной ветке введён `scripts/runtime-assets.mjs`. Список переносимых
файлов составляется из `src/assets/manifest.js` и небольшого списка
обязательных внешних ресурсов (иконки PWA, манифест и закреплённый Telegram SDK).
Vite использует `build.copyPublicDir: false`; после сборки плагин копирует
только разрешённые файлы и проверяет `dist/`. Отладочные `.map` отключены.
Добавлены тесты `tests/runtime-assets.test.js`. Арены для сайта копируются
из `public/locations/` по списку `active.json`. В тестовой сборке публикуется
отдельная страница редактора локаций и необходимые ей JS/CSS. Основная и
автономная сборки игры редактор не включают.

Существующие оптимизации не следует путать с новыми: загрузчик
`src/assets/preload.js` уже кэширует изображения по URL, а `PixiArena`
загружает уникальные адреса атласов один раз на сцену и переиспользует
источники для отдельных спрайтов. Рефакторинг повторяющихся Base64-значений
в сериализованном браузером SVG **ещё не выполнен**; он требует независимой
проверки PixiJS-парсинга и загрузки резервных SVG-изображений.

После публикации проверьте загрузку изображений и звука в игровых режимах, каталог арен и страницу редактора. Порядок проверки описан в [VALIDATION.md](VALIDATION.md).
