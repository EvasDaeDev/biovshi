# Биовши — локальная сетевая арена (LAN Multiplayer)
**Техническое задание и план реализации, v1.0**

- **Статус:** проектирование; реализация ещё не начата.
- **Ветка исходного проекта:** `main`. Опубликованные режимы описаны в [оглавлении](README.md).
- **Опора:** фактическая архитектура этой ветки.
- **Назначение:** реализация первого сетевого режима без внешних сервисов, с игрой в пределах одной локальной сети.
- **Приоритет:** сохранить существующие режимы Башни и тотализатора без регрессий.

> Документ фиксирует согласованные продуктовые правила и рекомендуемую архитектуру MVP. Числовые значения сетевых частот, таймаутов технической диагностики и производительности — стартовые параметры для тестов, не доказанные пределы движка.

## 1. Цели и границы версии

### 1.1. Цель
Пользователь запускает небольшой локальный сервер на компьютере, открывает «Биовши» в браузере и создаёт лобби. Остальные пользователи из того же Wi-Fi/LAN открывают локальный адрес игры на своих телефонах или компьютерах, видят список комнат, подключаются, выбирают пациента, подтверждают готовность. **Только хозяин лобби** нажимает «Старт». Хозяин может играть или оставаться наблюдателем, выполняя всю симуляцию на своём устройстве.

### 1.2. Что входит в MVP
- Полностью локальный режим без облачного сервиса и без необходимости выхода в интернет во время игры.
- ПК в роли локального HTTP/WebSocket-сервера для доступа к игре, комнатам и передачи сообщений.
- Один режим боя: настраиваемая дуэль / свободная схватка с произвольной смесью игроков и ИИ.
- Создание комнат, обнаружение через список, ручное «Обновить», автоматическое получение списка при открытии раздела.
- Основная кнопка «Старт» у создателя комнаты; «Готов» — у приглашённых игроков.
- Возможность хозяина играть или только наблюдать; любой другой участник может быть игроком или зрителем.
- Одиночный запуск: хозяин имеет право стартовать при одном бойце или при одном игроке с ИИ.
- Выбор арены, обычного профиля ИИ/пациента, собственной **временной копии** пациента из Башни, босса или статуса наблюдателя.
- Отображение параметров персонажей перед боем и в существующих боевых карточках, включая боссов.
- Авторитетная симуляция в браузере хозяина, синхронизация боевого состояния всем гостям.
- Переподключение гостя к своей сессии **не позднее 10 секунд**.
- Отключённая экономика: без ставок, платежей, наград, потерь и изменений Башни.
- Отдельные результаты без автоматического реванша; дальнейшие действия исключительно по решению хозяина.

### 1.3. Что НЕ входит в MVP
- Глобальные комнаты через интернет, облачный сервис лобби, NAT traversal, STUN/TURN, публичные матчи.
- Встроенный запуск LAN-режима внутри Telegram Mini App: он не гарантируется и будет исследован отдельно. Для MVP использовать обычный браузер.
- Нативное автоматическое обнаружение самого ПК-сервера без известного адреса; это ограничение браузерной платформы.
- Миграция хозяина во время матча и фоновый/headless расчёт физики в Node.js.
- Античит с проверкой законности всех улучшений; действует договорённость об игре по честным правилам между знакомыми.
- Автоматический матчмейкинг, команды, кооперативные миссии, отдельные камеры, голосовой чат, рейтинг, балансировка силы участников.
- Автоматический реванш, голосование за повторный бой.

## 2. Архитектура: полностью локальная сеть

```text
        одна локальная сеть / один роутер
 ┌────────────────────────────────────────────────┐
 │ ПК: Biovshi LAN Server (Node.js)               │
 │ • раздаёт собранную игру (HTTP)                 │
 │ • комнаты, присутствие, готовность (WebSocket)  │
 │ • пересылает игровые команды и снимки состояния │
 │ • НЕ рассчитывает физику и ИИ                  │
 └───────────────┬────────────────────────────────┘
                 │ LAN HTTP + WebSocket
       ┌─────────┼──────────────┐
       │         │              │
 ┌─────▼──────┐ ┌▼────────────┐ ┌▼────────────┐
 │ браузер    │ │ телефон     │ │ телефон     │
 │ хозяина    │ │ игрок       │ │ наблюдатель │
 │ симуляция  │ │ ввод+рендер │ │ только      │
 │ 60 Гц      │ │            │ │ рендер      │
 └────────────┘ └─────────────┘ └─────────────┘
```

**Важно:** компьютер, на котором работает LAN-сервер, и **хозяин комнаты** — логически разные роли. В типичном сценарии это один и тот же ПК (хозяин-наблюдатель), однако клиент с телефона тоже может быть хозяином *комнаты и симуляции*, пока LAN-сервер работает на ПК. Производительность мобильного хозяина проверяется тестами.

### 2.1. Почему WebSocket, а не WebRTC в первой версии
Для полностью локального прототипа с постоянно работающим ПК-сервером выгоднее использовать один WebSocket-хаб:
- не требуется сигнальный сервер отдельно от сервера лобби;
- нет STUN/TURN и настройки ICE;
- и игра, и соединение получают один локальный origin;
- легче реализовать вход, исключение участников, восстановление сессий и диагностику;
- трафик остаётся в LAN.

**Компромисс:** игровой поток пересылается **через локальный ПК-сервер**, а не напрямую peer-to-peer. Если процесс LAN-сервера остановится, обмен игровыми данными прекратится. В дальнейшем транспорт можно заменить на WebRTC, не меняя семантику сообщений и серверную модель комнат.

### 2.2. Доступ к серверу
- На ПК администратор запускает сервер, который слушает выбранный LAN-интерфейс; не публиковать порт в интернет.
- ПК показывает адрес вида `http://192.168.1.25:8080` и QR-код с этим адресом.
- Игрок с телефона впервые открывает адрес/QR в браузере; после загрузки игры список комнат получается **автоматически**, доступна кнопка «Обновить».
- Ссылка-приглашение и QR комнаты ведут на **тот же локальный сервер** с идентификатором комнаты, например `http://192.168.1.25:8080/?room=ABCD`. Ссылка работает только в доступной LAN.
- Участникам не нужно открывать Telegram или переходить на сторонний сайт для входа в конкретную комнату.
- Если устройства изолированы настройками Wi-Fi (guest isolation), соединение может не установиться; интерфейс должен показать понятную ошибку.

### 2.3. Интернет и безопасность контекста
- Сборка должна содержать необходимые ресурсы локально; проверить отсутствие обязательных CDN, внешнего шрифта, SDK и аналитического запроса на пути запуска LAN.
- ПК открывает игру по `http://localhost:8080` (для браузера это доверенный локальный origin).
- Телефоны открывают `http://LAN_IP:8080`. Это **обычно не secure context**. WebSocket/обычный игровой интерфейс работают, однако Screen Wake Lock и иные защищённые Web API там могут быть недоступны.
- На первом этапе **не обещать** антизасыпание телефона-хозяина при обычном HTTP. Для него нужны активный экран/системные настройки либо отдельное локальное HTTPS-решение с доверенным сертификатом.
- Telegram Mini App обычно требует HTTPS и при этом может блокировать доступ к локальным адресам. Поэтому использование Telegram для полностью автономного LAN в MVP **не входит в гарантированную поддержку**.
- Для общедоступных/недоверенных сетей простой HTTP/WS непригоден без дополнительных мер. MVP рассчитан на доверенный домашний Wi-Fi.

## 3. Роли

Два независимых атрибута:

| Сетевая роль | Игровая роль | Возможность |
|---|---|---|
| Хозяин | Игрок | Вся симуляция + управление собственным бойцом + «Старт» |
| Хозяин | Наблюдатель | Вся симуляция + общая камера + «Старт», без бойца |
| Гость | Игрок | Отправка команд движения, получение состояния, «Готов» |
| Гость | Наблюдатель | Только получение состояния и общая камера |

Сервер LAN не является хозяином симуляции. **Координатором матча служит браузер создателя комнаты**. В первой версии у каждой комнаты только один такой хозяин.

Наблюдатели **не занимают места бойцов** и не должны участвовать в проверке готовности. Жёсткого продуктового лимита зрителей для MVP нет, но их количество увеличивает сетевую нагрузку и измеряется отдельно.

## 4. Лобби, вход и старт

### 4.1. Экран сетевого режима
- При открытии отправить `rooms.list`; показать список комнат в ожидании.
- Кнопка «Обновить» повторяет запрос. Изменения списка могут приходить push-событиями WebSocket.
- Комната показывает: название, арену, число бойцов и игроков, количество ИИ, стадию «Ожидание/Идёт бой», доступность входа.
- «Создать комнату» доступна пользователю, подключённому к LAN-серверу.
- Комнаты с начавшимся матчем можно видеть в списке как недоступные, но **присоединение к ним невозможно**, включая режим зрителя. Исключение — восстановление своего ранее существовавшего соединения в течение 10 секунд.

### 4.2. Экран конкретной комнаты
Хозяин может:
- изменить имя комнаты, арену, состав/типы ИИ, число доступных игровых мест;
- назначить себе роль игрока или наблюдателя;
- выбрать своего бойца;
- видеть состав участников, их параметры, готовность и соединение;
- удалить участника из ожидания и закрыть комнату;
- нажать **«Старт»** при выполнении правил готовности.

Гость-игрок может:
- выбрать персонажа и увидеть собственные и чужие параметры;
- нажать **«Готов / Не готов»**;
- выйти из комнаты.

Гость-зритель не выбирает бойца, не нажимает «Готов», только наблюдает за ожиданием и затем боем.

### 4.3. Допуск к запуску
- Для старта достаточно **одного бойца**; это может быть хозяин либо ИИ, если хозяин только наблюдает. Режим с одним бойцом и без противников трактуется как тестовая/сценарная арена.
- Все **подключённые гости-игроки** обязаны подтвердить готовность; хозяин вместо «Готов» использует «Старт».
- При изменении гостем выбора бойца/параметров или изменении хозяином состава/арены готовность всех гостей-игроков сбрасывается.
- Хозяин нажимает «Старт» явно; автоматического запуска после готовности нет.
- Сервер проверяет полномочия хозяина, готовность, вместимость, наличие бойцов, совместимость версий и валидность конфигурации.
- Лобби блокируется до загрузки матча: новые входы и смена ролей больше не разрешены.
- Клиенты подтверждают готовность ресурсов (`match.loaded`), хозяин назначает сетевой tick начала и общий обратный отсчёт; запуск только после подтверждения всех уже подключённых клиентов либо отмена с понятной ошибкой.

### 4.4. После боя
- Общий результат: победитель/ничья/завершено хозяином, длительность, доступные достоверные показатели по бойцам.
- Нет денег, наград, опыта, прогресса и автоматического реванша.
- Все гости ждут решения хозяина; **только он** выбирает «Вернуться в лобби», «Подготовить новый бой» или «Закрыть комнату».
- Новый бой — отдельное действие хозяина; готовность гостей обнуляется; прежние настройки/персонажи могут быть предложены как начальные значения.
- Никакая кнопка гостя не запускает следующий матч.

## 5. Вместимость, арены, бойцы

### 5.1. Правила вместимости
- В общей сцене максимум **10 бойцов** для первоначальной реализации, включая людей, ИИ и боссов.
- **Любой босс считается одним бойцом** в логике количества слотов.
- Зрители не входят в вместимость арены.
- Предварительный лимит конкретной арены берём из действующего `TOWER_ARENA_CAPACITY` в `src/tower/floors.js`:

| Арена / id | Бойцов |
|---|---:|
| Операционная / `ward` | 8 |
| Ринг / `ring` | 3 |
| Кольцо / `annulus` | 4 |
| Шлюз / `sluice` | 5 |
| Зигзаг / `zigzag` | 7 |
| Колоннада / `columns` | 10 |
| Горловина / `throat` | 6 |

Это **предварительные проектные пределы генератора Башни**, а не подтверждённые результаты сетевого нагрузочного теста. Для большого босса коллизии должны проверяться по реальной анатомии; если безопасная расстановка невозможна, запуск запрещён с ясным сообщением. **Босс не расходует два или более игровых слота**, даже если крупнее обычного пациента.

### 5.2. Типы персонажей
- **Пациент из Башни:** создаётся одноразовая копия полного применимого состояния (характеристики, протезы, хирургия, мутации, анатомия, косметика).
- **Обычный профиль:** используются существующие `basic`, `fast`, `strong`, `agile`, `elite` и их визуальные настройки.
- **Босс:** выбрать одну из существующих анатомий, создать экземпляр независимо от номера этажа Башни; характеристики для сетевого боя должны быть явно определены конфигурацией персонажа и отражены в сводке.
- **Наблюдатель:** не имеет пациента и не вмешивается в бой.

В рамках доверительной игры полноценной проверки «законности» прокачки нет. Тем не менее сервер/хозяин должны отвергать некорректные типы сообщений, значения `NaN`, чрезмерно большие данные, недопустимые идентификаторы и небезопасную структуру объектов.

### 5.3. Параметры на экране
До старта показывать **всем** участникам сводку характеристик каждого бойца (игроков, ИИ и боссов):
- имя/профиль/тип, исходные очки и **эффективные** скорость, силу/критический шанс, манёвренность;
- состояние анатомии и важных протезов;
- влияющие на бой хирургические улучшения и мутации;
- для босса: разновидность, параметры и перечень особых действий.

Во время боя существующие карточки пациентов должны показывать соответствующие данные, включая боссов. Сетевые карточки строить из одного авторитетного описания персонажей от хозяина. Не отображать недостоверные «догаданные» параметры на клиенте.

### 5.4. Управление и атаки
- Человек управляет **только движением** пациента либо босса: виртуальный джойстик и, при наличии, выбор точки назначения.
- Все обычные удары срабатывают автоматически по текущим правилам.
- **Особые атаки боссов полностью решает и инициирует ИИ**; отдельной кнопки способности у человека нет.
- Управляемые человеком пациенты и боссы **могут атаковать во время движения**.
- При специальном движении/рывке босса ИИ на время анимационно-физического приёма может захватить управление траекторией; затем ручное движение возобновляется. Это не превращается в ручное управление спецатакой.
- Нужно разделить у босса `locomotion intent` (игрок) и `attack/ability decisions` (ИИ); сейчас они взаимосвязаны.

## 6. Порядок сетевой симуляции

### 6.1. Хозяин — единственный источник истины
Только браузер хозяина выполняет:
- физику, перемещение и повороты, ИИ, поиск целей, контактные проверки;
- расчёт атак, попаданий, отрыв конечностей, урона, смертей и победителя;
- окончательное разрешение команд гостей, выбор спавнов, случайные события.

Гости **не запускают локальную боевую физику, урон и ИИ**. Они передают лишь ввод, получают снимки состояния и события. Игровая камера у всех остаётся **существующей общей камерой**, вычисляемой локально по синхронизированным координатам бойцов; переключений камеры нет.

### 6.2. Начальные частоты для тестов
| Операция | Стартовое значение |
|---|---|
| `step(dt)` хозяина | фиксированный шаг 1/60 с |
| Отправка ввода гостей | 20–30 Гц плюс сообщение при изменении/отпускании |
| Пакеты снимков хозяина | 15–20 Гц, адаптировать по тестам |
| Отрисовка | существующий лимит до 30 FPS |
| События урона/отрыва/смерти | немедленно, надёжно и с нумерацией |

Использовать интерполяционный буфер на клиенте (~80–120 мс как стартовую гипотезу), ограниченный диапазон экстраполяции только для отображения и механизм сглаживания коррекций. Никакой клиентский урон/физический расчёт не должен подменять хозяина.

### 6.3. Ввод
Каждый `input` содержит `matchId`, `seq`, `clientTick`, `controllerId`, одну из команд:
- нормализованный вектор движения `x/y`, интенсивность в пределах [0,1], состояние отпускания;
- либо конечную точку маршрута в координатах арены — с проверкой границ хозяином.

Хозяин связывает `controllerId` с конкретным `robotId`, не доверяя переданному клиентом идентификатору робота. Старые/повторные `seq` отбрасываются. При потере управления сбрасывается «залипший» джойстик; персонаж удерживает позицию.

## 7. Протокол LAN

### 7.1. Транспорт
- HTTP раздаёт собранную Vite-версию игры, и сервер открывает WebSocket **на том же host:port** (например, `/lan/ws`).
- Сервер хранит комнаты, соединения и ключи доступа **в памяти**; долговременная база данных для MVP не требуется.
- Не публиковать протокол в глобальный интернет и не выполнять UPnP port forwarding.
- Сетевой модуль приложения не должен импортировать код графики/физики на сервере.

### 7.2. Общий конверт сообщения
```json
{
  "v": 1,
  "type": "room.ready",
  "roomId": "ABCD",
  "matchId": null,
  "requestId": "optional-unique-id",
  "seq": 18,
  "payload": {"ready": true}
}
```

Поля: `v` — версия протокола; `roomId` — комната; `matchId` — запущенный бой; `seq` — монотонный порядковый номер в рамках соответствующего потока. Авторизация идентичности — **по привязанной к WebSocket сессии**, не по произвольному `playerId` из `payload`.

### 7.3. Основные типы сообщений
| Отправитель | Тип | Назначение |
|---|---|---|
| Клиент → сервер | `hello` | версии приложения/протокола; получить идентификатор сессии |
| Клиент → сервер | `rooms.list` | запрос доступных комнат |
| Сервер → клиенты | `rooms.snapshot` / `rooms.changed` | список/обновления |
| Создатель → сервер | `room.create` | комната, роль хозяина |
| Гость → сервер | `room.join` | вход в комнату в ожидании |
| Гость → сервер | `room.ready` | подтверждение готовности |
| Участник → сервер | `room.select` | роль и конфигурация персонажа |
| Хозяин → сервер | `room.configure` | арена, ИИ, слоты и параметры |
| Сервер → участники | `room.state` | согласованное состояние лобби |
| Хозяин → сервер | `match.start` | блокировка входа и подготовка |
| Клиенты → сервер | `match.loaded` | подтверждение загрузки |
| Сервер → участники | `match.begin` | синхронизированный старт |
| Гость-игрок → хозяин | `input` | команды движения через сервер |
| Хозяин → гости | `state.snapshot` | состояние бойцов и мира через сервер |
| Хозяин → гости | `game.event` | атаки, повреждения, смерти, результаты |
| Сервер ↔ участники | `ping/pong` | доступность и задержка |
| Клиент → сервер | `session.resume` | восстановление прежней роли до 10 сек |
| Хозяин → сервер | `match.pause` / `match.resume` | остановка и возобновление после потери активности |
| Хозяин → сервер | `match.finish` / `room.return` / `room.close` | итог и решение хозяина |
| Сервер → участники | `error` | коды ошибок для интерфейса |

Имена являются **контрактом проекта**, реализация должна покрыть их тестами, допускается объединение вспомогательных сообщений при сохранении семантики.

### 7.4. Данные снимка
Минимально необходимы:
- `matchId`, номер simulation tick, игровое время, время создания снимка;
- все бойцы: идентификатор, координаты, углы, скорость/состояние движения, видимость, жив/выбыл;
- **поза** для отрисовки сегментов (не только `x/y/angle`): опоры, суставы, голова, позвоночник, дополнительные конечности, атака, прыжок/рывок, визуальные состояния;
- анатомия, список сегментов, HP/повреждения, отсутствующие сегменты, остатки и привязки визуальных ресурсов;
- необходимые параметры синхронизации эффектов, состояние финала, номера событий.

Схему сериализации нужно проектировать по реальному внутреннему `robotState`: текущий внешний API содержит геттеры и не предоставляет полноценного сеттера. **Не пытаться восстановить позу только вызовами `tick()` на клиентах** — это повторная симуляция и потенциальная рассинхронизация.

Реализовать пару адаптеров `captureAuthoritativeState()` / `applyRemoteState()` либо рендер-only `RemoteRobot`, не дублируя боевую физику. Базовый вариант — полный снимок с периодическими ключевыми кадрами; дельта-сжатие добавлять только по данным профилировщика. Эффекты, которые нельзя безопасно вывести из снимка, передавать как нумерованные идемпотентные события.

## 8. Состояния матча и потери соединения

### 8.1. Автомат состояний
```text
waiting → preparing → loading → countdown → running → results
    ↑                                               │
    └────── решение хозяина: возврат в лобби ───────┘
                          running → suspended → running
                               └───────────→ aborted
                  любое состояние → closed (хозяин)
```

- `waiting`: вход и изменение состава разрешены.
- `preparing/loading/countdown`: новые входы заблокированы.
- `running`: разрешён только `session.resume` прежнего участника в пределах 10 секунд.
- `suspended`: общее ожидание хозяина, физика остановлена; при возвращении полная синхронизация.
- `results`: новые входы запрещены до решения хозяина.

### 8.2. Отключение гостя
- Сервер помечает гостя отсутствующим и запускает **10-секундное окно** восстановления.
- Персонаж гостя не переходит под ИИ, прекращает ручное движение; оставшиеся атаки/физические реакции обрабатывает хозяин по правилам боя.
- В течение окна допускать `session.resume` с защищённым одноразовым/сессионным токеном, затем прислать полный снимок.
- По истечении 10 секунд право управления утрачивается до конца текущего матча. Никаких автоматических повторных подключений как новых игроков в текущий бой.
- При отключении зрителя бой никак не меняется.

### 8.3. Потеря хозяина
- При `visibilitychange`, приостановке браузера, невозможности продолжать simulation tick либо явной паузе хозяина — рассылается `match.pause`; клиенты показывают «Ожидание хозяина».
- Браузерное событие может не успеть отправиться перед сном; сервер должен также реагировать на пропавшие heartbeat/снимки состояния.
- Если хозяин восстановил активность, он отправляет **полный снимок**, сервер сверяет `matchId`, затем продолжает бой.
- Если хозяин закрывает комнату, явно выходит или не восстанавливается в пределах краткого интервала диагностики (начальная гипотеза 10 с) — завершить матч как `aborted`, без победителя и последствий.
- **Миграции хоста нет**. Если остановится сам LAN-сервер, соединение прервётся; игра должна корректно выйти в экран ошибки, а не зависнуть.

### 8.4. Wake Lock
- Хозяин при создании комнаты запрашивает `navigator.wakeLock.request('screen')`, если доступно, и показывает реальный статус: активен/отклонён/недоступен.
- Повторно запрашивать при возврате активной вкладки, снимать при закрытии комнаты.
- Wake Lock **не запрещает** ручную блокировку, сон ОС, закрытие крышки ноутбука или скрытие вкладки.
- Для ПК рекомендовать отключать системный сон на время боя. На телефоне при HTTP LAN Wake Lock может отсутствовать; это известное ограничение, а не скрытая гарантия.
- Нельзя переносить физику в таймеры фоновой страницы в надежде обойти ограничения браузера.

## 9. Боевые правила и отделение от экономики

- Сетевой режим — независимый `ctx.mode = 'multiplayer'` либо эквивалент с явным `matchContext`; старые `tower` и `spectator` сохраняют поведение.
- В `combatAttacks()` результаты должны направляться в независимый `settleMultiplayer()`, **никогда** в `bettingSettle()` / `settleTower()`.
- При **одном стартовом бойце** не срабатывать автоматически по правилу «остался один»; хозяин вправе завершить сценарий вручную.
- При полноценной схватке (два и более исходных бойца) победитель определяется существующей логикой последнего выжившего, если нет специальных условий тестового сценария.
- В сетевом режиме исключить запись ставок, заработков, операции с балансами, награды, изменения прогресса Башни, сохранение оторванных частей обратно в пациента.
- До входа в матч зафиксировать неизменяемые копии персонажей; по окончании их уничтожить вместе с контекстом боя.
- Общая камера как существующая в `src/render/camera.js`: вычисляется по живым видимым бойцам локально на клиенте, без переключений и отдельного управления наблюдателя.

## 11. Поэтапная реализация с критериями завершения

### Этап 0 — проверки архитектуры
- Зафиксировать работоспособность `npm test` в экспериментальной ветке.
- Провести аудит ассетов: офлайн-запуск после раздачи `dist`, отсутствие обязательной загрузки извне.
- Замерить длительность physics tick/рендера существующими средствами диагностики.
- **Готово, если:** базовая игра продолжает запускаться без подключения LAN-кода.

### Этап 1 — локальный сервер, комнаты и UI
- HTTP-раздача `dist`, WebSocket, состояния комнат, создание/поиск/обновление/готовность/«Старт»/закрытие.
- QR для адреса LAN-сервера и ссылки конкретной комнаты.
- Авторизация хозяина и привязка участника к соединению.
- **Готово, если:** два браузера на разных устройствах в одной сети видят одинаковое лобби, гостей нельзя запускать матч.

### Этап 2 — локальный multiplayer без сети в самой симуляции
- В одной вкладке создать переменный roster, назначить `local/remote/ai`, активировать свободные слоты.
- Нормальное ручное управление пациентом любого `id`.
- Разные профили/собственный пациент/босс в одном бою.
- Отдельные результаты, изоляция экономики; тест одиночного сценария.
- **Готово, если:** все эти случаи работают без соединения с удалённым браузером и не ломают Башню.

### Этап 3 — передача ввода и репликация
- Гость передаёт команды, хозяин ими управляет.
- Полные снимки всех бойцов и критические события.
- У гостя не работают `step()`, ИИ и урон.
- Интерполяция, карточки и общая камера.
- **Готово, если:** движения, отрыв частей, атаки, смерть и результат согласованы на ПК и телефоне.

### Этап 4 — полный цикл матча
- Готовность, загрузка, отсчёт, старт, результаты, решение хозяина.
- Запрет на новый вход во время матча, только `session.resume` до 10 с.
- Общее ожидание при потере активности хозяина, полный снимок при восстановлении.
- **Готово, если:** все переходы состояний и негативные сценарии покрыты тестами.

### Этап 5 — нагрузка и доработка
- Тест: ПК-хозяин-наблюдатель + 2 мобильных игрока.
- Тест: ПК-хозяин-наблюдатель + 4 мобильных игрока + ИИ до лимита выбранной арены.
- Тест: телефон-хозяин (при работающем ПК LAN-сервере) + другие телефоны.
- Сравнить качество графики, стоимость рендера/симуляции и сетевой поток, проверить боссов и все арены.
- Оптимизировать снимки/частоты по измерениям, а не заранее.
- **Готово, если:** для поддерживаемых конфигураций нет накопления отставания симуляции, нет расхождения результата и не теряются критические события.

## 12. Проверки при приёмке

### 12.1. Функциональные
- [ ] Без интернета, но при рабочем LAN два устройства открывают игру по адресу ПК-сервера.
- [ ] Список комнат появляется автоматически; кнопка «Обновить» отражает изменения.
- [ ] Ссылка/QR комнаты работает без стороннего сервиса, если клиент в той же сети.
- [ ] Создатель способен стать наблюдателем; остальные играют.
- [ ] Создатель способен играть; остальные играют либо наблюдают.
- [ ] Один боец без противников не завершает матч автоматической победой.
- [ ] «Старт» доступен только хозяину и только когда гости-игроки готовы.
- [ ] Зритель не занимает слот и не нажимает «Готов».
- [ ] Новый участник не подключается во время загрузки/боя/результатов.
- [ ] Гость, отключившийся менее чем на 10 с, возобновляет управление тем же бойцом.
- [ ] Гость, не вернувшийся за 10 с, не получает управление обратно в этом матче.
- [ ] Обычные пациенты и боссы атакуют автоматически **во время ручного движения**.
- [ ] Особые атаки боссов выбирает ИИ, а не клавиша игрока.
- [ ] Босс считается одним бойцом для лимита слотов.
- [ ] Параметры всех бойцов видны в подготовке и карточках боя.
- [ ] После завершения только хозяин определяет, что происходит с комнатой.
- [ ] Ни один сетевой бой не изменяет балансы, ставки и прогресс Башни.

### 12.2. Сетевые/стрессовые
- [ ] Состояние бойцов и расположение деталей тела согласованы на хозяине и гостях.
- [ ] Отрыв конечности появляется у всех один раз и в правильном состоянии.
- [ ] При искусственной задержке и потере пакетов интерфейс плавный, а результаты неизменно авторитетны у хозяина.
- [ ] Уход хозяина в фон останавливает симуляцию, остальные видят ожидание.
- [ ] Возврат хозяина восстанавливает единое состояние, без «ускоренного догоняния» огромного долга времени.
- [ ] Остановка LAN-сервера диагностируется и не оставляет бесконечно зависший экран.
- [ ] Потребление CPU/памяти и сетевой трафик измерены для 2/4/6/10 бойцов и отдельно с несколькими зрителями.
- [ ] Слабый телефон может снижать детализацию без изменения расчётов хозяина.

## 13. Угрозы, исключения и решения

1. **Сетевая реплика сложнее, чем управление.** `robot.js` хранит внутреннюю позу и создаёт графику; потребуется отдельный сериализатор и применитель снапшотов. Избегать имитации физики на госте.
2. **Смешение логики ИИ и атак босса.** Требуется разнести источники движения и способности, иначе управляемый босс потеряет рывки.
3. **Фоновая вкладка хозяина.** `requestAnimationFrame` останавливается/ограничивается; только честная общая пауза и контроль активности.
4. **Мобильный HTTP не secure context.** Wake Lock для хозяина-телефона может не работать; тестировать отдельно, не обещать невозможного.
5. **Большая анатомия и заполненная арена.** Валидация реального пересечения тел поверх формального лимита слотов обязательна.
6. **LAN-комнаты не видны до подключения к ПК-серверу.** Автообновление касается **списка комнат**, а не поиска самого серверного устройства.
7. **Зрители создают исходящий трафик** даже без физики. Без продуктового лимита, но с диагностикой и защитой от перегрузки.
8. **Публичный HTTP/WS небезопасен для недоверенных сетей.** MVP только для частной сети, с токенами ролей, проверкой пакетов и без внешнего проброса портов.

## 14. Минимальные меры защиты

- Сервер выдаёт непредсказуемые идентификаторы сессий, `hostToken` и отдельные `resumeToken`; не передавать права хозяина внутри клиентского `payload`.
- Не позволять обычным гостям `match.start`, изменять чужого бойца, задавать произвольный урон или пересылать от имени хозяина `state.snapshot`.
- Проверять типы, длины имён, размер сообщений, частоту `input`, число комнат и соединений, `roomId/matchId`, `seq`, URL-пути и origin.
- Обрабатывать HTML всех пользовательских имён как текст; не вставлять их через `innerHTML`.
- Сервер слушает только заданный LAN-интерфейс; предупреждать об открытии порта Windows Firewall/macOS Firewall.
- Не сохранять копии пациентов на сервере после закрытия комнаты и не логировать их полные конфигурации.
- Оставить возможность в будущем добавить локальный HTTPS/WSS без переписывания контракта сообщений.

## 15. Чего не начинать раньше времени

- Не переписывать текущую боевую математику ради сети.
- Не добавлять P2P/WebRTC или облачный лобби-сервис в первый локальный прототип.
- Не внедрять миграцию хоста и серверную симуляцию в Node.js.
- Не создавать интерфейс ручного управления спецатаками боссов.
- Не менять балансы и сохранения ради LAN-режима.
- Не делать отдельную камеру для зрителя.
